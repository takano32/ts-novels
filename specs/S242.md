# S242 PHP (mu-plugin ts-library・テーマ ts-bunko) のファイル構成と試験 (T45.1 の記録)

- 種類: 記録
- 状態: 有効
- 出典: 2026-11-05 の作業 (T45.1)
- 関連: T45.1, T45, S181, S19

mu-plugin `mu-plugins/ts-library/` を、WordPress を使わない部分 (判断・計算・文面) と WordPress に触る部分 (フック・DB・出力) と WP-CLI のコマンドに分け、小さなファイルに割った記録。外から見える振る舞い (`wp ts` の名前・引数・出力、フック、ショートコード、option・meta、URL と応答、HTML) は分割前 (`0e8c7712`) と同じにした。分割の後に純粋な関数へ出したもの・試験を足したもの・型の寛容さを旧に揃えたものも、行ごとに T45.1 の小タスクにある。

## ファイルの構成

`ts-library.php` は `includes/files.php` の `TS_Library_Files` の 3 つの表に書いたファイルだけを、表の順に require する。glob は使わない。配備 (`scripts/wp/deploy.sh`) は rsync に `--delete` を付けないので、消したり名前を変えたファイルが本番に残る。glob で読むと残った古いファイルまで読まれ、関数の二重定義で落ちる。

| 表 | いつ読むか | 中身 |
|---|---|---|
| `PURE` | いつも (最初) | WordPress を使わない部分。単体の試験はこの表だけを WordPress なしで読む |
| `WP` | いつも (`PURE` の後) | WordPress に触る部分。先頭は `site-hooks.php` (`TS_Library::boot` の `pre_get_posts` を、索引と年別の一覧の `pre_get_posts` より先に登録するため。後から登録した側が `posts_per_page` と `orderby` を上書きする) |
| `CLI` | `WP_CLI` のときだけ (最後) | `wp ts` のサブコマンド。`TS_Command_Base` を継ぐサブコマンドごとのクラスで、最後の `commands/register.php` が `WP_CLI::add_command` で登録する |

`PURE` の中の順は、読み込み時に別のクラスを要らないので意味は無い (クラス定数と静的メソッドは呼ぶときに引く)。`WP` と `CLI` の中は、フックの登録の順と、継承 (`TS_Command_Base` が先) の順。

## WordPress を使わない部分と使う部分の境目

`PURE` の表のファイルは、PHP の組み込み関数と `PURE` の中で定義した関数とクラスしか呼ばない。WordPress の関数・グローバル変数 `$wpdb` に触るもの (DB・フック・出力・エスケープ・日時の表示 `wp_date`・`sanitize_title`・`wp_json_encode`) は `WP` と `CLI` の側に置き、純粋な側には値か callable で渡す (例: `TS_Work_Index::child_slugs` の `$sanitize`、`TS_Takedown_Input::validate` の `$resolve` と `$is_email`、`TS_Takedown_Rules::params` の `$defined`)。エスケープは呼び出し側で行い、純粋な側はエスケープ済みの文字列を受ける (例: `TS_Takedown_Text::respond('invalid', …)` の `items`)。

境目は `scripts/wp/tests/files.php` が機械的に見る: `PURE` の各ファイルを `token_get_all` で読み、関数呼び出し (直前が `->`・`?->`・`::`・`function`・`new` でない名前の直後に `(`) のうち、組み込み関数でも `PURE` の外側で定義した関数・クラスでもないものが 0 件で、`$wpdb` も 0 件。理由つきの許可リストはいまは空 (`is_email` は T45.1.20 で注入に替えて外した)。さらに、どのファイルも `$GLOBALS` を使わない (要求の中の状態はクラスの static プロパティに置く。T45.1.19.4)。

純粋な側へ出さなかったもの:

- import の hash (`md5(HASH_VER . wp_json_encode(…))`) は WordPress 側に残す。`wp_json_encode` は不正な UTF-8 を直してから符号化するので、純粋な側で `json_encode` に替えると hash が変わり得る。hash が変わると本番の全投稿が updated になり、手動編集の保護の判定も動く。
- 子孫の集め方 2 本 (`wp ts apply-takedown` の再帰 `TS_Takedown_Command::descendants` と、申請の適用の stack `ts_takedown_target_posts`) は WordPress 側に 2 本のまま残す (T45.1.19.3。下の「判断」)。子の問い合わせだけ `ts_takedown_child_ids` (`includes/takedown/takedown-apply.php`) に 1 つにした。

## 試験

`make test-php` (`scripts/wp/php_test.sh`) で流す。手元に PHP が無く、docker も立てない決まりなので、`scripts/wp/deploy.sh` の構文検査と同じ形で、対象を tar でサーバに送り、一時ディレクトリに展開して `php -l` (本番の PHP 8.0.30) と `scripts/wp/ts_library_test.php` を流して消す。公開ルートと DB には触れない。

### WordPress の代わり (T45.1.14)

WordPress に触る側 (`WP`・`CLI`・テーマ) を WordPress なしで動かすために、`scripts/wp/tests/wp-stubs.php` に WordPress の関数と同じ名前の最小の代わりと、配列の置き場 (`TS_WP_Stubs`: 投稿・meta・term・option・transient・ユーザ・cron) を置いた。

判断: WordPress の関数を callable で注入する設計には変えず、代わりを置く。理由は 3 つ。(1) `WP` の表のファイルを本番と同じ形のまま読める (注入にすると、フックを読み込み時に登録する順と、テーマが名前で呼ぶ 19 関数の互換に響く)。(2) 旧版 `0e8c7712` のコードも同じ代わりで動かせるので、HTML の試験の期待値を実装の写しでなく旧版の出力から取れる (T45.1.15)。(3) 代わりは `scripts/wp/tests/` にだけあり `includes/` には無いので、`PURE` の境目の検査 (`files.php`) と「`PURE` を WordPress なしで読む」ことは変わらない。代わりは `PURE` にも依存しない (URL 基底は `TS_WP_Stubs::$post_type_slugs` に持ち、`register_post_type` が上書きする)。

代わりは出力の構造 (タグ・class・順・文言) を固定するためのもので、エスケープの忠実さ (`esc_url` の正規化、`esc_html` の実体の扱い、`sanitize_title` の日本語) は見ない。本番の HTML との一致は T45.3.1 の基準で見る。本物と違うところ (同じ日付の並びは ID の昇順、`time()` は置き換えられない、`wp_insert_post` と `wp_update_post` が書く `post_modified` は `TS_WP_Stubs::$now`、`get_posts` が見る引数の範囲、`$wpdb` は SQL を解釈せず `$db_rows` に積んだ行を返す、`render-lookup.php` と `index-render.php` の static キャッシュは 1 プロセスに 1 度) は `wp-stubs.php` の先頭に列挙してある。

使い方 (詳しくは `wp-stubs.php` の先頭):

- 置き場は `TS_WP_Stubs::reset()` で空にし、`add_post`・`set_meta`・`add_term`・`set_terms`・`set_term_meta`・`$options`・`$users`・`$caps`・`$is`・`$queried`・`$query_vars` で作る。置き場を作る関数は `scripts/wp/tests/wp-fixtures.php` に置き、試験と probe が同じものを呼ぶ (中身を変えると期待値を取り直すことになるので、足すだけにする)。
- `echo` する部品は `TS_WP_Stubs::capture(fn)` で文字列に受ける。ショートコードは `TS_WP_Stubs::shortcode('ts_removed_list')`。init のフックは `TS_WP_Stubs::run_init()`。
- フックの記録は `TS_WP_Stubs::$hooks` と `hook_list()`。書き込みの記録は `$log` (`wp_update_post`・`update_option`・`status_header`・`nocache_headers` など) と `$mails`。`wp_die` は `TS_WP_Die` を投げるので catch して `title` と `args['response']` を見る。
- 旧版のコードを同じ代わりで動かして期待値を取る: `scripts/wp/php_probe.sh <probe.php> scripts/wp/tests/wp-stubs.php scripts/wp/tests/wp-fixtures.php --old 0e8c7712:mu-plugins/ts-library/includes/render.php`。probe は代わり → fixtures → 旧版のファイルの順に `require` し、同じ fixture の関数で置き場を作って `capture` の結果を `var_export` で出す。旧版のファイルは新版と同じ関数名を定義するので、新版の `WP` の表 (と `PURE`) は読まない。取った値は試験に貼り、出典 (リビジョン・日付・probe の名前) をコメントに書く。部品が多いものは「部品/投稿」の鍵の配列に集め、旧版の出力の `var_export` と鍵ごとに比べる (`render-html.php` の `$same`)。`render-html.php`・`takedown-wp.php` の HTML の期待値は全部この手順で取った (書誌カード 4 通り、部品 8 つ × 投稿 5 つとサイドバー、帯と子の状態、索引 4 つ、ショートコード 2 つ、作品カード 6 枚、題名)。サイドバーの検索窓のようにテーマのファイル (`searchform.php`) を読む部品は、probe にも `themes/ts-bunko` を送る。
- 人が触る経路 (フォームの送信と確認リンク・cron・運営委員の操作・`apply-takedown`・`export-takedowns` ほか。T45.6.4・T45.6.5) は、場面を作るだけでなく流し方も `wp-fixtures.php` の `ts_fixture_run_*` に置き、試験と probe が同じ関数を呼ぶ (新版と旧版で名前の違う関数・クラスは callable で渡す)。`time()` は置き換えられないので、時刻は `ts_fixture_rel` で「いま」からの差 (時間の単位に丸める) にして比べる。`$_POST`・`$_GET`・`$_SERVER` は `ts_fixture_request_run` が置いて、終わったら元に戻す。
- `wp-stubs-check.php` は代わりそのものの決まり (meta の single と複数、`get_posts` の既定と並び、`get_the_terms` の無いとき false、階層の permalink、`wp_die` が止まる、フックは priority の順) を固定する。代わりを直すときはここも直す。
- `CLI` 側は `ts_library_test.php` の `WP_CLI` の代わりの上で流す。出力は `WP_CLI::$out` に [種類, 文] で残り、`WP_CLI::error` は `TS_CLI_Error` を投げる (T45.1.7.5。例は `tests/commands-wp.php` の `wp ts reset`)。
- テーマのテンプレートは `get_header`・`have_posts`・`the_post`・`the_content` の代わりがあるので、`TS_WP_Stubs::$loop` に投稿を置き、`$is`・`$queried`・`$query_vars` を立てて `locate_template('index.php', true, false)` で読める (`load_once` を false にしないと 1 プロセスで 1 度しか描けない)。テーマの判断を mu-plugin へ移したとき (T45.1.5) は、場面 `ts_fixture_theme` の上で全部のテンプレートを描く probe を、移す前のコミット (`git ls-tree` で集めた mu-plugin とテーマの全部の .php を `--old <コミット>:<パス>` で送る) と作業木の両方で流し、出力が同一であることを見た。

## 配備の手順 (T45.3)

配備の前後で本番の見え方を比べる道具は `scripts/wp/deploy_snapshot.sh` (読むだけ。T45.3.1)。

- `take DIR` で取るもの: 主要 URL 19 か所の応答コードと本文の sha256、`wp ts verify` の出力、`wp ts export-takedown-urls` を並べ替えたもの。
- 本文の sha256 は、写り込むキャッシュバスターを伏せ、タグの区切りで行に割って並べ替えてから取る。同じ日付の作品の並びは流すたびに変わるため。
- トップとページ送りのある作者ページは、載る作品そのものが変わるので、応答コードだけを比べる。
- 「今日の一作」は日付で変わるので、前後は同じ日に取る。
- 2026-11-05 に配備前の本番で 2 回続けて取り、2 組とも差が無いことを確かめた。

配備は高野さんがホームから `scripts/wp/deploy_run.sh` で流す (T45.6.1。2026-11-05 の配備 (T45.3.3) で scratchpad から流したスクリプトをリポジトリに入れたもの)。既定は dry-run で、本番に書くのは `--apply` のときだけ。dry-run でも読むだけの段 (見え方・md5・取り下げの印) は本当に流し、書く段は何をするかを表示する。見え方とログは `.deploy/<日時>/` に残る (git 管理外。`--out DIR` で変えられる)。

```sh
cd ~/GitHub/ts-novels && git pull --ff-only
scripts/wp/deploy_run.sh            # dry-run。先に必ず流して、rsync の一覧と段の順を目で見る (S67)
scripts/wp/deploy_run.sh --apply    # 実配備
```

段は次のとおり (本番に書く段に *)。

1. 手元の確認。HEAD が origin/master の最新で、`mu-plugins/`・`themes/` に未コミットの変更が無い (rsync は作業木を送る)。違えば止まる。
2. 配備前の見え方を取る (`deploy_snapshot.sh take`)。
3. * 復旧点 `wp db export ~/dumps/pre-deploy-<日時>.sql` (S67)。
4. * `deploy.sh --skip-php`: 構文検査・サーバ側 repo・生成物 (`bodies/`・`payloads/`)・robots.txt・画像。PHP を置く段 (mu-plugin・テーマ) は飛ばす。

## 純粋な関数に出したときの判断 (T45.1.16 以降)

- `TS_Episode_Fields::body` (T45.1.16.2) は `--bodies` の有無を 3 つ目の引数 `$bodies` で受ける。状態とペイロードの 2 つだけでは「メタのみ投入 (null)」と「ペイロードが無い (案内文)」を分けられないため。ペイロードのファイルを読むのは `includes/commands/import.php` に残し、取り下げ対象なら読まないのも分割前と同じ。
- `TS_Work_Index::parent_term_values` (T45.1.16.3) は、連載の親 work に合併する値を work ごとに束ねずに、話ごと (episodes の添字 => work と taxonomy ごとの値) に返す。import は分割前と同じく話ごとに `TS_Term_Resolver::term_ids` を呼び、term ID で束ねる。束ねてから 1 度に呼ぶと、解決できなかった値を数える順 (`ts_term_warnings` と警告の「上位」の並び。`arsort` は同点なら入れた順) が変わるため。
- `wp ts verify` の親 work の期待値 (`TS_Verify_Expect::assignment_counts` の `parent_expect`) は `parent_term_values` を使わず、別の実装のまま残す。verify の役目は importer と独立に数え直して取り違えを見つけることで、同じ関数を使うと importer の誤りを期待値も写してしまう。
- `TS_Import_Decision::decide` (T45.1.16.1) は手動編集の検出を bool でなく callable で受ける。検出は DB を読む (`_ts_last_import_gmt` と `post_modified_gmt`) ので、分割前と同じく「投稿があり、hash が違い、`--overwrite-manual` が無い」ときだけ呼ぶため。bool で受けると呼び出し側が先に読むことになり、hash が同じで skipped になる投稿 (通常の import の大半) でも読んでしまう。3 か所 (work・話・単発の fill) の違いは引数にある: 単発の fill は親 work が必ずあるので `$exists` が true (dry-run でも updated)、hash のキーは `_ts_fill_hash`。読み取りと分岐の順は `includes/commands/import.php` の `decide` (private) に 1 か所にまとめた。
- `TS_Takedown_Plan::request_apply` / `request_reinstate` (T45.1.17.3) は、対象と子孫の今の値 (`ts_takedown_target_states` が集める post_id => `ts_takedown_post_state`) を先に全部読んでから、触る投稿を決める。分割前は 1 投稿ずつ読んで変えていたが、1 投稿の値 (状態と取り下げのメタ) はほかの投稿の変化に依らず、対象の列は重複が無いので結果は同じ。代わりの上で旧版と新版を同じ場面 (別の記録で取り下げ中の話・移行前の draft・旧版の孫・結びつかない URL を含む申請) で動かし、投稿の状態・option `ts_takedown_urls` の順・申請の状態と記録・メール 4 通の宛先と文面が一致することを `scripts/wp/tests/takedown-wp.php` が固定している。
- 子孫の集め方 2 本は 1 本にしない (T45.1.19.3)。`wp ts apply-takedown` の `descendants` は再帰で、子を `get_posts` の順 (既定の日付の新しい順) に深さ優先で並べる。申請の適用の `ts_takedown_target_posts` は stack で、子を `get_posts` の逆順 (日付の古い順) に並べる。代わりの上で子 2 つ (と孫 1 つ) の作品を集めると、再帰は [新しい話, その孫, 古い話]、stack は [古い話, 新しい話, その孫] になる (`scripts/wp/tests/takedown-wp.php`。stack の側の期待値は旧版を同じ代わりで動かした出力)。この順は dry-run の行と option `ts_takedown_urls` (→ `wp ts export-takedown-urls` の出力) に出るので、1 本にすると片方の順が変わる。子を引く問い合わせ (post_type ts_work・post_parent・post_status any・posts_per_page -1・fields ids) は同じなので、そこだけ `ts_takedown_child_ids` に 1 つにし、2 本はそれを呼ぶ。
