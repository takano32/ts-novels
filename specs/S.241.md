# S.241 管理画面での編集を原本に反映する機能 (2026-10-31 高野さんの方針)

- 種類: 設計
- 状態: 有効
- 出典: 2026-10-31 高野さんの発言
- 関連: T.44, S.5, S.10, S.20, S.100, S.109, S.114

## 現状

編集の経路は、WordPress の外 (git の `catalog/` と `content/`) に保管している原本を書き換えて、本番に反映する流れだけ。
管理画面で作品・話・作者 term・分類 term を直しても、次の import や全消し再構築で消え、`wp ts verify` は手動編集として NG に挙げる (S.100)。
例外は固定ページで、`wp ts export-pages` で管理画面の編集を `content/pages/` に書き戻せる (S.109。往復の確認は配備後)。

## 方針

**管理画面での編集を原本に反映する機能も作っていく** (2026-10-31 高野さん)。
S.5・S.10・S.20 の「管理画面での手動編集は禁止」は、この機能ができるまでの決まりとする。原本を優先する (反映した後の原本から本番を作り直せる) 形は変えない。

## 案: 正本を WordPress に移す (2026-10-31 高野さん「いい方法があればそちらを採用したい」)

双方向の同期 (管理画面の編集を原本へ書き戻す) を作るより、ある時点で**正本を WordPress に切り替え、向きを一方向にする**案。

- **切り替えの時期**: 原本から機械的に作り直す作業 (作品クラスタの裁定 T.24.4、版違いの整理 T.25、取り下げの論理削除) が終わった時点。それまでは今の形 (原本 → 本番) のまま。
- **切り替えた後**: 編集は管理画面 (WordPress のリビジョンが履歴になる)。git へは WordPress から定期的に書き出す (`wp ts export` を新設し、作品・話のメタを JSONL、本文を Markdown で `catalog/` に。差分が読めるバックアップと、原本アーカイブの `path_map.json` の元になる)。DB のダンプも定期的に取る。
- **失うもの**: 「いつでも原本から全部作り直せる」こと。`wp ts reset` と全量の `wp ts import` は切り替え後は使わない (誤って流さないよう止める)。構造の変更は作り直しではなく、WP-CLI のコマンドで本番の投稿を直接直す形になる。
- **変わらないもの**: 原本アーカイブ (GitHub Pages) は静的なまま。取り下げは WordPress 側の申請と運営委員の操作が正になり、denylist は書き出しで作る。

## 未決 (T.44.1)

- 対象: 作品・話の本文とメタ、作者 term、分類 term、解題のうちどこまでか。
- 方式: 管理画面の編集を overrides ファイル (`catalog/episode_overrides.yml` など) に書き出すか、原本そのものを書き換えるか。
- 書き戻しの起点: `wp ts export-pages` と同じくコマンドで書き出してコミットするか、保存のたびに記録して後でまとめるか。
- 原本側と管理画面側の両方が変わったときの扱い。
