## 72 時間の明記をやめ、専用フォーム → 10 日後に自動取り下げ → 運営委員がオーバーライド

**現状**:

- 公開中の `/takedown/` (`content/pages/takedown.html:2`) は「申し出の確認から 72 時間以内」と約束し、窓口は **GitHub の Issue** (`:6`)。しかし **リポジトリの Issue は無効** (`gh repo view`) で、**窓口が機能していない**。さらに S.28・S.75 は「GitHub Issue 窓口は不採用 (依頼者の身元と依頼内容を公開の場に晒す)」と決めており、**ページが設計に反している**。runbook の言う「メール + フォーム転送」のフォームは存在せず、メールアドレスも書かれていない。
- 72 時間の記述は **14 ファイル・33 箇所** (S.113 の表)。公開面 3 枚 (about `:17` / takedown `:2` / removed `:17`)、作者への連絡文の下書き (S.85〜S.91 `:85`) を含む。
- 自動化の下地: WP-Cron は閲覧駆動 (`DISABLE_WP_CRON` 未定義) で、前段キャッシュが PHP を呼ばない閲覧では動かず、低トラフィック時に遅れる。サーバ crontab は使える。`wp_mail` は `sendmail_path` 設定済み (送達未検証)。REST 200 / xmlrpc 403 / wp-login 403 (CloudSecure)。`/removed/` は**手書きの静的ページ** (生成器は無い。runbook の /removed/ への掲載 (S.80) の「catalog から再生成」は未実装)。
- `apply-takedown` は denylist.yml (git) を唯一の入力にしており、WP 側で状態が変わる仕組みは無い。

**仕様 (決定案) — 状態機械**:

```
[フォーム送信] → unconfirmed ─(確認メールのリンク)→ received (確認時刻) ─(確認時刻から 10 日, cron)→ applied
                     │ 7 日で未確認 → expired                    ↑           │
                     │                      運営委員: approved (即時適用) ─┘   reinstated (復帰)
                     │                      運営委員: rejected (自動適用を止める。理由は内部メモ)
```

1. **窓口**: `/takedown/` に mu-plugin のフォーム (`admin-post.php` の nopriv アクション。外部プラグインなし)。項目: 当時のペンネーム / 対象 URL (複数可) / 連絡先メール / 立場 (作者本人・権利継承者・その他) / 本人確認の手がかり (任意) / 自由記述 / 名前の掲示可否。スパム対策: nonce・honeypot・送信所要時間・IP 単位 rate limit (transient)・**確認メール必須**。GitHub Issue の記載は削除し、メール窓口を併記。
2. **保存**: CPT `ts_takedown_request` (`public=false`、管理画面は運営委員のみ)。連絡先は WP の DB にだけ置き (dump は私有ストレージ)、リポジトリには書かない (S.215 (元の `takedown/README.md`) の約束を維持)。`wp ts reset` の対象に**入れない**。
3. **自動適用** (`applied`): 対象投稿 (+ 子) を `private` + `_ts_visibility=withdrawn`、`ts_takedown_urls` 更新、`/removed/` は **WP の withdrawn 投稿から動的生成**に切り替える (手書きをやめる)。
4. **運営委員の操作**: 申請の編集画面にボタン 3 つ (承認して即時適用 / 却下 / 復帰)。却下は自動適用を止めるだけで記録は残す。
5. **通知** (`wp_mail`): 受付 → 依頼者に確認リンク / 確認 → 運営委員全員 (「YYYY-MM-DD に自動適用」) / 確認時刻から 7 日 → 運営委員にリマインド / 適用・却下 → 依頼者 + 運営委員。
6. **cron**: サーバ crontab `*/10 * * * * cd ~/novels.xwp.jp/public_html && wp cron event run --due-now` と wp-config `DISABLE_WP_CRON` (高野さんの作業。`wp-config.php` は公開ルート外にあり、手で入れる)。
7. **denylist.yml との整合**: WP で `applied` になった申請は `wp ts export-takedowns` が denylist 形式で出力 → セッションが追記してコミット → 原本アーカイブのビルド除外 (T.35.2) に伝播。**denylist.yml = git に残す確定記録、申請 CPT = 運用の原本**。手動エントリ (S.222〜S.235) は従来どおり denylist → `apply-takedown`。
8. **原本アーカイブの自動化 (任意)**: `deploy-pages.yml` がWP サイトの公開 REST `GET /wp-json/ts/v1/withdrawn` (source_path の一覧だけ。依頼者情報は含めない) を取り込んで除外すれば、人手なしで 10 日後に原本アーカイブからも消える。
9. **文言**: 公開面から「72 時間」を全部外す。案: 「フォームからのお申し出は、確認メールの到達から **10 日後に自動的に非公開**になります。運営委員が内容を確認し、早めることや、本人確認が取れない場合に保留することがあります」。作者連絡文 (S.88) も同じ趣旨に。S.75〜S.81 を改訂する (SLA 節 → 自動適用の仕組み、WP サイトの非公開化 (S.76)・本番 .htaccess の 410 (S.77)・原本アーカイブ側の除外 (S.78) の時間指定を撤去)。

**既存の裁定との衝突と解消**: S.30 の削除窓口の項・S.40・S.41・S.42 が維持してきた「72h SLA の宣言」→ **S.43 で撤回** (安全弁の正体は「人の即応」ではなく「自動適用 + 人のオーバーライド」になる)。「GitHub Issue 窓口は不採用」は**維持** (現ページの記載が誤り)。「本人確認は緩く」は維持しつつ、確認メールで最低限の実在性だけ担保する。
