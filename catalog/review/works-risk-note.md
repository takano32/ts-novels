# 作品クラスタを自動生成のまま採用した場合のリスク(1 ページ)

**判断は済んでいます** — サイト所有者の決定により、作品 slug(実測 1,453 件。うち機械候補 1,298)と
分類語彙 slug(実測 1,407 件。うち機械候補 1,377)は **自動生成のまま採用**します。
人間が読むのは判断のためではなく、**どこがどう壊れうるかを把握しておくため**です。
読んで承認する必要はありません。

対象データ: `catalog/works.jsonl`(Work 1,463 件 / episode 3,844)と
`catalog/work_overrides.yml`(`needs_review` の雛形 361 行 = 現行 328 件 + 旧版の残骸 37 件)。
生成元は `scripts/wp/work_builder.py`。
用語は [`docs/glossary.md`](../../docs/glossary.md) が正典
(**本館 / 別館 / 旧館** は内部用語で、読者に見せる文面では使わない)。

---

## 0. なぜ「作品クラスタの誤り」が URL に効くのか

設計 3.2 のパーマリンクは **話が作品の下に入れ子**になります:

| 種別 | URL |
|---|---|
| 作品 | `/works/johdan-d-upboy/` |
| 話 | `/works/johdan-d-upboy/06/` |

つまり **クラスタリングを間違えると、その作品だけでなく配下の全話の恒久 URL が変わります**。

**実測した影響範囲**:

| 数字 | 値 |
|---|---|
| Work 総数 | 1,463 |
| `needs_review: true` の Work | **328**(22.4%) |
| その配下の episode | **1,930 / 3,844(50.2%)** |
| うち slug が pykakasi 由来(題名を直すと slug も変わる) | 286 Work |
| 題名を直しても slug が変わらない(ASCII 題名) | 42 Work |

半分の話の URL が「機械の推測したクラスタ」に乗ります。ただし**後述のとおり大半は実害が小さい**
(束ね方が多少違っても、その作品の中に正しく居る)。危ないのは §1 の C・E・F・G と §2 です。

## 1. 類型・件数・実害

`needs_review` が立つ条件は 3 つ(重複あり): 根拠が弱い / 15 話以上 / 複数ディレクトリ。
これに**題名の壊れ方**を掛け合わせて分類しました。

| # | 類型 | 件数 | 何が起きるか | 実害 |
|---|---|---|---|---|
| **A** | 弱い根拠だけの **2 話**クラスタ(同一ディレクトリ) | 96 | 同じ投稿ディレクトリの連番ファイル 2 本を束ねただけ。ほぼ正しい | **小** |
| **B** | 弱い根拠だけの **2 話**クラスタ(**別ディレクトリ**) | 59 | 無関係な単発 2 本が題名の共通接頭辞で誤って束ねられうる | **中** |
| **C** | 弱い根拠だけの 3〜14 話(別ディレクトリ) | 18 | 同上。話数が多いぶん誤りが目立つ | **中** |
| **D** | 弱い根拠だけの 3〜14 話(同一ディレクトリ) | 90 | 投稿バッチ = 連載なので概ね正しい | **小** |
| **E** | **15 話以上**の大クラスタ | 34 | 「作者の全作品」が 1 作品に潰れている恐れ。例 `mashiro_yuu-hanayochanshiriizusettei`(43 話・題名「華代ちゃんシリーズ設定」) | **大** |
| **F** | 題名が**助数詞で切れている** | 19 | slug に意味のない語尾が残る。例 `kamikawa_ayano-hontounojibun-dai`(題名「本当の自分 第」)、`yamu-…-sono`(「〜その」) | **中**(URL の見栄えのみ) |
| **G** | 題名の**括弧が閉じていない / HTML 片が残る** | 18 + **3** | 例 `hotaru-visuteia-chapter`「ヴィスティア (chapter」、`kebo-megamikamenmiimiru`「女神仮面ミーミル**<**」。`<` の混入はパーサのバグ | **中**(3 件はバグ) |
| **H** | 題名が**ファイル名のローマ字**のまま | 38 | 例 `mashiro_yuu-ahujouri01`「AHujouri01.」、`zock-yuuki`「yuuki」。読者に題名として出る | **中** |
| **I** | 題名が 3 文字以下 | 13 | 例「絆」「奥義」「変革」。同名衝突しやすい | **小** |
| **J** | 作者が特定できない `unattributed` 配下 | 22 | slug が `unattributed-…` になり、作者ページからたどれない | **中** |

C と E は重なります(合計の重複を除いた実数は 328)。

**A・D(186 件)が全体の 57%** で、ここは実害が小さい。実際に見るべきは **B・C・E・G・H・J(190 件、重複あり)**。

## 2. `needs_review` が立っていないのに危ないもの(重要)

自動判定は次の 3 つを見逃しています。**`needs_review: false` なので雛形にも出ていません**。

### 2-1. 同一シリーズが 2 つ以上に分割されている(prefix ペア 88 組)

題名が別題名の接頭辞になっている Work のペアが **88 組**、うち**尾側が 1〜2 話しかないものが 70 組**。
つまり「本編クラスタ」+「番外編/改訂版が独立した小クラスタ」という形です。

```
johdan | 着せ替え少年 (19話) ←→ 着せ替え少年6 北へ (1話) / 着せ替え少年 お年賀スペシャル (1話)
                              ←→ 着せ替え少年4 ときめきメモリアル (1話) / …計 7 個に分裂
johdan | 戦乙女セーラ (69話)  ←→ 戦乙女セーラ」VS (2話)
baretto| デュアルワールド (25話) ←→ デュアルワールド・リライト (5話)
```

**実害: 中**。読者が「着せ替え少年」の作品ページに行っても第 4・5・6 話が居ない。
ただし**作者ページ(`/authors/johdan/`)には全部並ぶ**ので、完全に迷子にはなりません。

### 2-2. タイトルページ / 目次が単独の Work になっている(9 件)

```
johdan-kisekaeshounen-meinpeeji     「着せ替え少年 メインページ」 (1話, needs_review=false)
johdan-senotomeseerameinpeeji       「戦乙女セーラメインページ」 (1話, needs_review=false)
writerman-…-mokuji                  「「聖霊戦隊ホーリーレンジャー」目次」 (1話)
unattributed-untitled-document      「Untitled Document」 (1話)
```

本来は親 Work の `title_pages` に入るべきものが、独立した 1 話作品として並びます。
**実害: 小〜中**。作品一覧に中身のない項目が 9 個混じる。

### 2-3. `work_overrides.yml` のキーが一意でない(10 組)

雛形のキーは `"<作者slug>|<作品題名>"` ですが、この組が**重複する Work が 10 組**あります
(work_slug は `-2` で一意化されているのにキーは同じ)。

```
johdan|とらぶる☆すぴりっつ        → johdan-toraburu-supirittsu (10話) と …-2 (3話)
sky_high|ヒーロー誕生!?           → sky_high-hiirootanjou (8話) と …-2 (2話)
kamikawa_ayano|本当の自分 第      → kamikawa_ayano-hontounojibun-dai (4話) と …-2 (2話)
kion_rei|絆 / johdan|同居人 / maki_takashi|華代ちゃんシリーズ / baretto|アナログ所さん /
sky_high|次元管理人フォスター・シリーズ / s_haneoka|卯年 / yays|奇術
```

- **今回は overrides を使わないので実害なし**。
- ただし**将来 overrides で直そうとしたとき、どちらの Work に効くか決まりません**。
  修正する場合は `work_builder.py` のキーを `work_slug` に変える必要があります(§4)。
- そしてこの 10 組はそれ自体が **2-1 の分割の証拠**でもあります(同じ題名の Work が 2 つある)。

### 2-4. `work_overrides.yml` に旧版の残骸が 37 行

現行の `works.jsonl` に対応する Work が無いキーが 37 行あります
(`None|…` という作者 slug、`aki_michiru|姫神奇譚 第` など)。前回生成時の名残で、
**今の catalog には効きません**。混乱の元なので `make catalog` での再生成時に一掃するのが望ましい。

## 3. 「そのまま採用」の総合評価

| 観点 | 評価 |
|---|---|
| 話が失われる | **なし**。orphan 0 で全 3,844 話がどれかの Work に属す。掲載漏れは起きない |
| 話が間違った作者に付く | **なし**(作者同定は Work クラスタと独立。ただし別件で 1 件あり → §5) |
| 作品ページの中身が変になる | **あり**。§1-E の大クラスタ 34 件と §2-1 の分割 88 組 |
| 恒久 URL が後で変わる | **あり**。直す場合は 1,930 話ぶんの URL が動きうる → 301 リダイレクトが必須 |
| 読者が作品にたどり着けない | **ほぼ起きない**。作者ページ・ジャンル・キーワード・年別・検索の 5 経路が並行してある |

**結論**: 公開を止めるほどの問題は無い。最大の副作用は「作品ページの粒度が場所により不揃い」で、
これは**後から直せる**(次章)。

---

## 4. 後から直す手順

catalog が単一真実源で import が冪等なので、**直して再インポートすれば反映されます**。

1. `catalog/work_overrides.yml` を編集する
   - `work_title:` を書き換えると slug 候補も作り直される
   - **その前に `scripts/wp/work_builder.py` の override キーを `work_slug` に変える**
     (§2-3 の 10 組の曖昧さを消すため)
2. `make catalog` → `catalog/works.jsonl` 再生成 → 差分を確認
3. **旧 slug → 新 slug の対応表を作る**。`wp ts export-pathmap` の出力を再生成前後で diff する
4. 本番の `.htaccess` に 301 を追記(`docs/publish-runbook.md` の手順)。
   **恒久 URL を無告知で捨てない**のがこのプロジェクトの原則
5. `wp ts import` → `wp ts verify`。2 回目が created=0 / updated=0 になることを確認
6. 👤 nginx キャッシュクリア

**直すなら早いほうが安い**。公開前(Phase 7 の解禁前)なら 301 も不要です。

## 6. 旧目録の非表示エントリについて(参考)

旧目録 lib01–06 の HTML コメント内に伏せられていた **12 エントリは「区別なしで収録」**が
サイト所有者の決定です。Work クラスタ上も他の話と同等に扱われます
(実装は別セッション)。本文書の件数はこれらを含みます。
