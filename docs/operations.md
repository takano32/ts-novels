# 運用の手引き

WP サイトを公開 (配備) する、失敗を戻す、判断を変えてやり直す、削除依頼に応える、作業場所を移す、という
運用の流れを説明します。実際に打つコマンドは各節が指す S にあり、ここでは「何をどの順で、なぜ」を書きます。
仕組みの説明は [architecture.md](architecture.md) にあります。

## 前提: 誰が何をするか

- **作業の基本** — 担当タスクを TASKS.md と関連する S で確かめ、受け入れ条件を満たすまでやります。
  新しいスクリプトは `scripts/wp/` に置いてツールの一覧 (S.210) に 1 行足し、コミットは日本語で書きます (S.5、S.10)。
- **人にしかできないこと** — 作者や関係者への連絡、所有者の判断、本番のキャッシュの全消し、管理画面の操作です。
  TASKS.md では「(八重洲さんの判断)」「(高野さんの作業)」のように誰の何かを書いてあり、
  実行するセッションはそこに当たったら飛ばして、最後に「人の判断・作業待ち」として報告します (S.3、S.12)。
- **エージェントは作者や関係者に連絡しません** (S.5、S.87)。
- **本番で危ないことをする前に復旧点を作ります**。DB は `wp db export`、`.htaccess` は日付つきの控えです (S.10 の 5、S.67)。

## 公開 (配備)

公開とは、目録データ (`catalog/`) を作り直し、そこから本番の WordPress を作り直すことです。
WordPress の DB は使い捨てなので、迷ったら「catalog を直して投入し直す」のが常に正しい道です (S.69)。

流れは次のとおりです (S.69、チェックリストは S.71)。

1. **開発機で目録を作り直す** — `make catalog` を流し、`catalog/QA.md` を目で確かめます。
   catalog に差分が出なければ公開する必要はありません。差分が意図どおりならコミットして push します
   (配備スクリプトは push 済みのコミットしか運ばないため。S.83)。
2. **配備する** — `scripts/wp/deploy.sh` を引数なしで流して dry-run の内容を見てから、`--apply` で配備します (S.69)。
3. **本番で復旧点を取る** — `wp db export` で DB を書き出します。ここから先はこれを戻せば元に戻せます。
   ダンプは私有の保管場所へ移し、公開リポジトリには入れません (S.69、T.38.1)。
4. **本番で投入する** — `sync-terms` → `import` の dry-run → `import` → `apply-takedown` の順です。
   `import` の `--bodies` には必ず `payloads/` を渡します。`bodies/` を渡すと全話の本文が仮の文に置き換わります (S.69、S.83)。
   もう一度 `import` を流して `created=0 / updated=0` になることで、投入が冪等であることを確かめます (S.69)。
5. **確かめる** — `wp ts verify` と、キャッシュ回避の `?_cb=` を付けた curl で主要な URL を見ます (S.69)。
6. **キャッシュの全消しを高野さんに頼みます** (S.69 の 6)。
7. **原本アーカイブ** — WP の URL が変わったときだけ、`wp ts export-pathmap` の結果をコミットして原本アーカイブを配信し直します (S.69 の 7)。

公開のたびに、DB のダンプ・`QA.md` の数値・かかった時間を残します (S.71)。

### 失敗したときの戻し方

| 症状 | 対処 |
|---|---|
| 投入が途中で落ちた・おかしなデータが入った | 手順 3 のダンプを `wp db import` で戻す |
| `.htaccess` を変えたら関係ない URL が 500 や 403 になった | 日付つきの控えを戻す |
| 反映されない | キャッシュ回避つきの curl で確かめ、正しければキャッシュの全消しを頼む。それでも駄目なら調べる |
| catalog が壊れた | git で戻して `make catalog` を流し直す。catalog は生成物なので手で直さない |

(S.70)

## やり直し (判断を変えて作り直す)

レビューで NG が出たときなどに、判断を変えてやり直す手順です (S.72〜S.74)。

- **手で直してよいのは入力だけ** — 判断を書くファイル・スクリプト・設計です。
  生成物 (`catalog/*.jsonl`、`QA.md`、`bodies/`、WordPress の DB) を手で直しても次の生成で消えます (S.72)。
- **直したいことと直す場所の対応** — slug は `catalog/slug_overrides.yml`、作品のまとめ方は `catalog/work_overrides.yml`、
  話の作者は `catalog/episode_overrides.yml`、語彙は各 `*_map.yml`、本文の変換は `scripts/wp/body_convert.py`、
  特定の作品を非公開にするなら `takedown/denylist.yml`、方針そのものは設計に改訂の章を書き足します (S.72)。
- **やり直しの型** (S.73)
  - A: catalog を作り直して投入する (上書きファイルや目録の解析を直したとき)。投入は冪等なので何度流しても安全です
  - B: 本文だけ作り直す
  - C: WordPress の `ts_*` を全部消して最初から投入する。いちばん確実です。消した後は、目録からは戻らないアイキャッチ画像の設定をやり直します
  - D: 本番に何が載っているかは `ts_catalog_commit` で分かり、その時点の入力を git で再現できます
- **URL が変わるやり直しに注意** — slug を変えると別の投稿になるので、A では古い URL の投稿が残ります (S.73)。
  公開中なので、古い URL から新しい URL への 301 を付け替え表 `catalog/redirects.yml` から作ります (S.151)。
  全部消すか、catalog に無い投稿だけを片付ける方式にするかは T.24.7 で決めます (S.152)。
- `wp ts reset --yes` は Claude Code の権限の仕組みに止められるので、必要なときは所有者に手で打ってもらいます (S.83)。
- **NG の受け付け方** — 「URL (または episode_id) と何が違うか」を 1 件ずつ受け取り、上の対応表に振り分けます (S.74、S.95)。

## 削除依頼への対応

依頼に応えることは最大掲載原則の安全弁です (S.41、S.43)。手順は S.75〜S.81 で、
所有者レビューの決定によってまさに作り直している最中なので、**いまの手順**と**予定の手順**を分けて書きます。

### いまの手順

S.75〜S.81 の流れに、S.43 で撤回された「72 時間以内」の約束を外したものです (S.43 の決定 2)。

1. **受け取る** — 依頼の実物は私有の保管場所に置き、リポジトリには入れません。`takedown/denylist.yml` に項目を足し、
   消える URL を作品・全話・別名・原本のパスまで洗い出します (S.75)。
2. **WP サイトから外す** — 復旧点を取ってから `wp ts apply-takedown` を流します (S.76)。
3. **410 を返す** — `scripts/wp/htaccess_block.py` で `.htaccess` の自分のブロックを書き換え、
   対象が 410、関係ない URL が 200 のままであることを確かめます (S.77)。
4. **原本アーカイブから外す** — 配信時の除外がまだ無いので、リポジトリから該当ファイルを消してコミットし、push 後に 404 を確かめます (S.78)。
5. **git の履歴から消す** — 依頼者が配布そのものを止めてほしいと明示したときだけ行います。
   既に配られたクローンや第三者のアーカイブまでは遡れないことを依頼者に伝えます (S.79)。
6. **`/removed/` に掲示する** — 作者名・作品名・理由の要約・時期だけを載せます (S.80)。
7. **仕上げ** — `denylist.yml` の各段に日付を入れて `applied`、確かめたら `verified` にし、キャッシュの全消しを頼み、依頼者に完了を知らせます (S.81)。

いま公開中の窓口 (`/takedown/`) は無効な GitHub Issue を案内しているので、メール窓口に直すまでは依頼が届かない状態です (S.112)。
直すのは T.17 で、窓口のアドレスの承認 (八重洲さんの判断) が先です (T.17.1)。

### 予定の手順

- T.23 の後は、2 段目が `draft` ではなく `private` になり、3 段目の 410 は WordPress が返すので `.htaccess` には画像だけが残ります (S.119、S.121、S.123)。
- T.26 の後は、フォームの申請が状態機械に乗り、確認から 10 日後に自動で非公開になります。運営委員は承認・却下・復帰・期限変更ができます (S.126〜S.128)。
  フォームで取り下げた分は `wp ts export-takedowns` で `denylist.yml` に書き写してコミットします (S.132)。
- 予定の仕組みは、テスト作品 1 件で実際に流す削除リハーサルで確かめ、その結果で S.75〜S.81 を書き直します (S.46 の 7.2、T.26.8)。

## 作業場所の移設

作業機を別のサーバに移すときは、git clone すれば続きができますが、git 管理外のものが 4 つあります (S.82)。

- Python 環境 `.venv/` は `make venv` で作り直します (版は Makefile で固定)。
- 本文の生成物 (`bodies/` `payloads/` `payloads-docs/`) は作り直し、目録の差分 0 と本番との一致 (checksum の比較で転送予定 0 件) を確かめます。これが移設の検証になります。
- サルベージ途中の資材 `~/ts-novels-holding/` は作り直せないので rsync で運びます。
- Claude Code の memory はコピーします (S.84)。

移設が終わった判定は S.84 にあり、2026-10-26 に新しい機で全項目を確かめています (S.84)。
注意点 (配備は push 済みのコミットだけ、`--bodies` には `payloads/`、curl にはキャッシュ回避) は S.83 です。

## 定期の作業

公開後の定常運用として次を予定しています (S.47、T.38)。

| 頻度 | 作業 |
|---|---|

| 年 2 回 | WP サイトと原本アーカイブの両方のリンクを全部たどって検査する (T.38.3) |
| 年 1 回 | 素の環境から作り直す演習 (T.38.4)。移設 (S.82〜S.84) が初回の実績 |
| 依頼のつど | 削除依頼への対応 (T.38.5) |

## 文書の更新

- 終わった T は記録の S に写してから tasks/ と TASKS.md から消してよく、TASKS.md と tasks/ にしか無い情報は作りません (SPECS.md の決まり 3、S.13)。
- S を変えたら状態と関連を更新し、SPECS.md の一覧の行も直します。覆された S は本文を消さずに状態を「一部失効」「失効」にします (SPECS.md の決まり 5)。
- 方針を変えるときは設計に改訂の章を書き足します。書き換えずに追記するのが慣例です (S.72)。
- S を変えたら、この docs/ の関係するところも直します (SPECS.md)。
