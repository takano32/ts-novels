# 仕組み

原本の置き場所から WP サイトに表示されるまでの流れと、それぞれの部品の役割をまとめます。
コマンドの細部や判定基準は括弧内の S にあります。

## 全体の流れ

```
旧サイト (消滅)
  │  Wayback・CommonCrawl・ウェブ魚拓・作者のサイトから回収 (S.156〜S.159)
  ▼
git リポジトリ takano32/ts-novels (公開)
  │  原本 18,006 ファイル + catalog/ scripts/ takedown/ content/ mu-plugins/ themes/ など (S.49、S.58)
  │
  ├─[master に push]─▶ .github/workflows/deploy-pages.yml ─▶ 原本アーカイブ (GitHub Pages)
  │                       リポジトリ直下をそのまま配信 (S.58)
  │
  └─[開発機] make catalog ─▶ catalog/ (目録データ) と bodies/ (本文 Markdown)   (S.69)
              payload_build.py ─▶ payloads/ (投入用の本文 HTML)               (S.188)
              scripts/wp/deploy.sh --apply ─▶ 本番サーバ                     (S.69)
                                                │
                     [本番] wp ts sync-terms / import / apply-takedown / verify (S.69)
                                                ▼
                                   WP サイト https://novels.xwp.jp
```

WP サイトの各話の書誌カードから「原本を見る」で原本アーカイブへ行けます。逆向きの案内 (原本アーカイブから WP サイトへ) は
まだ無く、T.35 で入れます (S.15、S.94 の「原本アーカイブ側からの案内バナー」)。

## 二つの公開面

| | WP サイト | 原本アーカイブ |
|---|---|---|
| URL | `https://novels.xwp.jp` | GitHub Pages (`takano32/ts-novels`) |
| 中身 | 目録で体系化した図書館 (WordPress の投稿) | 旧サイトの URL の形をそのまま保ったミラー |
| 配備 | rsync と `wp ts import` | `master` への push で自動 |
| `.cgi` を含む URL | 配信できない | 静的なファイルとして返せる |
| ヘッダの制御 | `.htaccess` で検索避けや 410 を返せる | できない。取り下げは 404 で妥協 |

この表は S.68 の要約です。二つに分けたのは、移築先のサーバが `.cgi` を名前に含む URL を一律に拒否するからで、
原本にはそういうファイル (CGI が出力した画面の保存) が 9,021 本あります (S.56、S.63)。
原本アーカイブは原本を改変せずに残す層で、WP サイトは読書と発見のための層です (S.15)。

## 原本アーカイブ

- リポジトリのディレクトリが旧サイトの世代とホストに対応しています。直下が `ts.novels.jp`、`~yays/` が八重洲メディアリサーチ、
  `~ezpe/` が最旧のホストなどです (S.50、S.51)。
- いまは `deploy-pages.yml` がリポジトリ直下をそのまま配信しています (S.58)。メールアドレスの除去・WP サイトへの案内・
  検索避け・取り下げ分の除外は、配信時に加工する `scripts/wp/annex_inject.py` として T.35.2 で作る予定で、まだありません (S.44、S.78)。
- GitHub Pages は `.cgi` のファイルを `application/octet-stream` で返すので、ブラウザがダウンロードしてしまいます。
  中身は CGI の出力画面の保存で、スクリプトのソースではありません (S.110)。直し方は T.16.5 で検証します。
- 読者のメールアドレスや投稿者の IP アドレスが掲示板のログに残っています。扱いは所有者の判断待ちです (S.155、T.31)。

## 目録データ (catalog)

`catalog/` が**単一の真実源**です。WordPress の DB は使い捨ての派生物で、`wp ts import` でいつでも作り直せます。
管理画面で作品を直接編集することはせず、直したいことは `catalog/` の上書きファイルに書きます (S.10 の「catalog を単一真実源とする決まり」、S.5)。

| ファイル | 中身 |
|---|---|
| `episodes.jsonl` | 話の一覧 (3,844 話)。1 行 1 話 (S.69) |
| `works.jsonl` | 作品の一覧。連載は複数の話をまとめたもの (S.16、S.176) |
| `authors.json` | 作者 (322 名) (S.176) |
| `terms.json` | ジャンル・種別・キーワード・共有世界・収蔵区分の語彙 (S.69) |
| `*_overrides.yml` `*_map.yml` | 人の判断を書く上書きファイル。slug・作品のまとめ方・話の作者・語彙の正規化 (S.72) |
| `reports/` と `QA.md` | 各段の集計。`QA.md` は公開の前に目で確かめる (S.69、S.180) |

各欄の意味は S.212 (episodes.jsonl)・S.213 (authors.json)・S.214 (provenance) に、ファイルと再生成は S.211 にあります。

- **話と作品** — 話 (Episode) は読者が 1 回で読む単位で、目録の 1 項目に対応します。
  作品 (Work) は連載やシリーズをまとめた単位で、目録には無いので合成します (S.16)。
- **episode_id** — すべての段をつなぐ鍵です。原本のパスの `/` を `__` に置き換えたもので、
  `episodes.jsonl` の値をそのまま使い、作り直しません (S.8)。
- **収蔵区分 (corpus)** — 話の出自の分類です。正規目録 (lib1–73) 2,887、旧目録 (lib01–09) 97、
  目録外の収蔵 859、文庫未掲載、道場 (未投入) があります (S.16)。
- `make catalog` は決定的で、同じ入力からは同じ出力が出ます。2 回続けて流すと差分は 0 です (S.72、S.180)。
  `make check` は書き込みをしない自己検査です (S.180)。

## 本文の変換

- 原本の HTML を Markdown に変換し、「タグ・空白・山括弧を除いて正規化した文字列が原本と完全に一致する」ことを
  機械で確かめます。これを**無損失証明**と呼び、通った話だけ Markdown を正とします。通らない話は原本の HTML のまま載せます (S.18、S.37)。
- 結果は 3,644 話中 3,642 話が合格、原本のままが 2 話です (S.177)。変換器は `scripts/wp/body_convert.py` (S.177)。
- 変換結果の `bodies/` は git 管理外で、`make catalog` で作り直します (S.58)。

## 投入用の本文 (payload) と配備

- `scripts/wp/payload_build.py` が開発機で Markdown を WordPress のブロック HTML に変換し、`payloads/` に出します。
  サーバの PHP に Markdown の変換器を入れないためです (S.188)。
- メールアドレスはここで本文からも除き、出荷前に残りが 0 であることを機械で確かめます (S.10 の「メールアドレスを DB に入れない決まり」)。
- 運営文書 (編集"好"記・巻頭言など) は `scripts/wp/docs_build.py` が `payloads-docs/` に出します (S.82、S.200)。
- `scripts/wp/deploy.sh` は引数なしで dry-run、`--apply` で実際に配備します。push 済みのコミットしか配備せず、
  `--delete` は使いません。配備の前に全 PHP をサーバの PHP で構文検査します (S.69、S.83)。
  運ぶもの: サーバ側のリポジトリ (`~/novels.xwp.jp/repo`)・`bodies/`・`payloads/`・`payloads-docs/`・mu-plugin・テーマ・画像・`robots.txt` (S.69)。

## WP サイトの中身

### mu-plugin `ts-library`

`mu-plugins/ts-library/` に置いた自作プラグインです。管理画面から無効にできない場所なので、事故で中身の構造が消えません (S.19)。

- 投稿タイプ: `ts_work` (作品と話。親が作品、子が話)、`ts_doc` (運営文書)、`ts_dojo` と `ts_board_post` (登録のみ。T.36 で使う) (S.21、S.181)
- 分類: 作者・ジャンル・種別・キーワード・共有世界・収蔵区分の 6 種 (S.181)
- 表示の部品 (`includes/render.php`: 書誌カード・話の前後ナビ・パンくず・サイドバー) と索引 (`includes/indexes.php`) (S.165、S.101)

### `wp ts` コマンド

WP-CLI から使うコマンドで、`includes/commands.php` にあります (S.19、S.182)。

| コマンド | 役割 |
|---|---|
| `sync-terms` | 作者と語彙を投入 |
| `import` | 作品と話を投入。何度流しても同じ結果になり、2 回目は `created=0 / updated=0` が受け入れ条件 (S.10 の「インポートを冪等にする決まり」) |
| `apply-takedown` | `takedown/denylist.yml` に従って取り下げる |
| `verify` | 件数・未所属・分類の付き方を catalog と照合する |
| `export-pathmap` | 原本のパスから WP の URL への対応表を出す |
| `reset --yes` | `ts_*` の投稿をすべて消す (やり直し用) |
| `sync-pages` / `sync-docs` | 固定ページ (`content/pages/`) と運営文書を投入 (S.200) |

`import` は投入した時の catalog のコミットを `ts_catalog_commit` に記録するので、本番に何が載っているかを後から再現できます (S.73、S.182)。
予定のコマンドとして、ロールを整える `role-sync` (S.116)、固定ページを git に書き戻す `export-pages` (S.109)、
フォームの取り下げを記録に書き出す `export-takedowns` (S.132) があります。

### テーマ `ts-bunko`

`themes/ts-bunko/` のテーマで、外部の CDN や Web フォントを読みません (S.192)。
話ページには文字サイズ・行間・明朝/ゴシック・ダークモード・しおり・左右キーでの話送りの操作列があります (S.193)。

### 主な URL

| URL | 中身 |
|---|---|
| `/novel/<作品>/` と `/novel/<作品>/<話>/` | 作品と話 (S.21、S.26) |
| `/authors/<作者>/` | 作者ページ (S.26) |
| `/genre/` `/type/` `/keyword/` `/world/` | 分類ごとの一覧 (S.26、S.192) |
| `/year/<年>/` | 年別の一覧 (S.195) |
| `/index/` 以下 | 作者さくいん・年表・分類さくいん・キーワードさくいん・オススメの環・運営文書 (S.194) |
| `/docs/` 以下 | 運営文書・ギャラリー・にせ乙女パラダイスの記録 (S.197、S.200) |
| `/about/` `/archive/` `/takedown/` `/removed/` | 固定ページ 4 枚 (S.200) |

検索は WordPress の標準検索に分類の絞り込みを足したものです (S.39 の「検索方式の改訂」、S.196)。
`/boards/` と `/dojo/` は当時の掲示板の投稿者の名前が載る層なので、公開後も恒久的に検索避けします (S.10 の「掲示板層を恒久 noindex にする決まり」、S.42)。
`robots.txt` は AI の学習用クローラを拒否し、ia_archiver は許可しています (S.170)。

## 本番環境の制約

本番は Xserver for WordPress で、接続は `scripts/wp/novels-ssh` を使います (S.60)。

```
ブラウザ ─▶ nginx (キャッシュ) ─▶ Apache (.htaccess) ─▶ PHP 8.0.30 ─▶ WordPress 7.1 ─▶ MariaDB
```

(S.62)

- **キャッシュ**: 前段の nginx がキャッシュするので、確認の curl には毎回 `?_cb=<乱数>` を付けます。
  キャッシュの全消しは管理パネルの操作で、高野さんにしかできません。「反映されない」ときはまずキャッシュを疑います (S.62)。
- **`.cgi` などの拒否**: `.cgi` `.pl` `.py` `.sh` `.phar` `.shtml` `.shtm` を名前に含む URL は 403 になり、改名でも避けられません (S.63)。
- **`wp-config.php` が公開ルートの外にある**ので、rsync の `--delete` は禁止です (S.61)。
- **管理画面はセッションから開けません**。ログイン URL は変えてあり、その値を文書やコミットに書いてはいけません。
  確認は WP-CLI と curl だけで行います (S.66、S.10 の「ログイン URL の変更値を転記しない決まり」)。サーバのログも読めません (S.61)。
- `.htaccess` には自分のマーカーブロックの中しか書かず、全文をリポジトリに持ち込みません (S.64)。
- web 経由の処理は 180 秒で止まるので、投入は必ず WP-CLI で行います (S.62)。サーバの Python は 3.6 と古いので、変換は開発機で行います (S.65)。
- 危険な操作の前に確かめることは S.67 のチェックリストにまとまっています。

## 取り下げの仕組み

取り下げの記録は `takedown/denylist.yml` の 1 ファイルで、これが WP サイト・`.htaccess`・原本アーカイブの処理を動かします (S.18)。
依頼者の連絡先はリポジトリに書きません (S.43、S.125)。

### いまの仕組み

| 段 | 何をするか | 出典 |
|---|---|---|
| WP サイトの投稿 | `wp ts apply-takedown` が対象と子の話を `draft` にする | S.76 |
| `.htaccess` | `scripts/wp/htaccess_block.py` が取り下げた URL に 410 を書く | S.77 |
| 原本アーカイブ | 配信時の除外がまだ無いので、リポジトリから該当ファイルを消してコミットする (404 になる) | S.78 |
| git 履歴 | 依頼があったときだけ除去する | S.79 |
| `/removed/` | 作品名・作者名・時期を掲示する (いまは手書きのページ) | S.80、S.112 |

いま取り下げているのは、作者の申し出による 9 作品 (S.222〜S.230)、オフ会レポート 2 件 (S.231〜S.234)、
Marie 氏の作品 7 作 (S.235。2026-10-27、T.18) で、本番では 51 件の投稿が `draft` です (S.97、S.98、T.18.2.3)。
公開中の `/takedown/` は GitHub Issue を窓口として案内していますが、Issue は無効で、設計でも採らないと決めた経路です。
暫定のメール窓口に直すのが T.17 です (S.112)。

### 予定の仕組み (S.43)

- **非公開の表し方** — `draft` をやめて `private` にし、理由をメタ `_ts_visibility` (`withdrawn` = 取り下げ / `superseded` = 旧版) で持ちます。
  優先順位は 取り下げ > 旧版 > 公開 です (S.117)。
- **応答** — 読者には WordPress が 410 (取り下げ) か新版への 301 (旧版) を返し、運営委員としてログインした人には本文と帯を見せます (S.118)。
  `.htaccess` の 410 は WordPress を通らない画像だけに残します (S.119)。nginx のキャッシュがログインを素通しするかを先に実測します (S.120、T.23.1)。
- **ロール** — 「運営委員」(閲覧と申請の処理) と「運営委員 (編集可)」(固定ページと解題の編集も) の 2 種です (S.116)。
- **フォーム** — `/takedown/` のフォーム → 確認メール → 確認から 10 日後に自動で非公開 → 運営委員が承認・却下・復帰・期限変更で上書きします (S.124〜S.130)。
  `/removed/` は非公開にした投稿から自動で作り (S.131)、フォーム経由の取り下げは `export-takedowns` で `denylist.yml` に書き写して git に残します (S.132)。
- 原本アーカイブにはログインが無いので、取り下げ分は除外 (404) のまま、旧版は原本としてそのまま置きます (S.43)。

## 版違いと作品のまとめ直し (予定)

- **作品のまとめ直し** — 自動で束ねた連載に別の作品が混ざっている疑いが 71 作品あります。
  `catalog/work_overrides.yml` に分割・切り離し・併合を書けるようにし、束ね直して URL が変わったものは旧 URL から 301 で転送します (S.107、S.146、S.151)。
- **版違いの整理** — 同じ作者の同じ題名で別ファイルの組が 303 組あります。新しい掲載日の版を残し、
  本文が一致するか類似度 0.95 以上なら自動、それ以外は人が確かめます (S.106、S.139、S.144)。
  これは「載せない」ではなく版の整理で、最大掲載原則の例外には入れません (版違いは新しい版を残す決定。S.43)。
- まとめ直しを先に、版違いを後に行います (S.146)。
